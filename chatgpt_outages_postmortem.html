LESSONS LEARNED
Case Study 1: Architectural Insights

Khi Auth Sập, Tại Sao User Có Thể Thấy 404?

TẠI SAO TRẢ 404 THAY VÌ 401/403?
Architectural Masking & Routing Fallback
  • Security & Privacy (RFC 9110 §15.5.5): Origin server có thể trả 404 để che giấu sự tồn tại của tài nguyên nếu request chưa qua xác thực hợp lệ.
  • Gateway / Ingress Layer: Khi Auth verification fail tại gateway, request bị chặn ngay lập tức, không được proxy vào backend route.
  • SPA Client-Side Fallback: Single Page App không nhận được auth state hợp lệ, router ở client không match view và rơi về route 404 mặc định.
BẪY GIÁM SÁT KHI AUTH SẬP
The Silent Failure Trap (Khái Niệm Vận Hành)
  • Requests bị chặn/reject ngay từ cổng Auth layer trước khi tới API core.
  • Core backend hoàn toàn khỏe mạnh (CPU thấp, error rate = 0) vì không nhận traffic.
  • Monitoring nếu chỉ bám vào backend metrics 🟢 sẽ thấy hoàn toàn bình thường.
  • User thực tế chỉ thấy lỗi 404 hoặc blank page, tạo nên độ trễ phát hiện sự cố.
Cam kết khắc phục của OpenAI (Postmortem Write-up): (1) Tự động dọn dẹp stale configuration, (2) Cơ chế staged recovery & rollback tự động, (3) Pre-deployment validation & hệ thống cảnh báo xung đột, (4) Tăng cường auth resilience.

QUY CHUẨN RFC 9110 & DIỄN GIẢI KỸ THUẬT
503 Service Unavailable vs 404
  • HTTP 503 (RFC 9110 §15.6.4): Server hiện không sẵn sàng xử lý request, thường do quá tải tạm thời (temporary overload) hoặc đang bảo trì (maintenance).
  • HTTP 404 (RFC 9110 §15.5.5): Server không tìm thấy representation phù hợp hoặc từ chối tiết lộ tài nguyên.
  • Góc nhìn kiến trúc (Diễn giải): Về mặt kiến trúc, 503 có thể phù hợp với overload hoặc upstream failure, nhưng đây là diễn giải kỹ thuật chứ không phải RCA đã được xác nhận từ OpenAI.

ENGINEERING RECOMMENDATIONS
Khuyến Nghị Kỹ Thuật: Phòng Ngừa & Giảm Thiểu

Cam Kết Khắc Phục Của OpenAI & Khuyến Nghị Cho Team

1. DEPLOYMENT SAFETY (TỪ POSTMORTEM OPENAI)
  • Config validation trước deploy — schema check & diff review tự động
  • Staged recovery & automated rollback trigger khi error rate vượt ngưỡng
  • Tự động dọn sạch stale configuration, tránh xung đột cấu hình
  • Thêm pre-deployment validation và cảnh báo sớm về incompatibilities
2. AUTH RESILIENCE (BEST PRACTICES)
  • Auth failure → graceful degradation, tránh tình trạng block all-or-nothing
  • Cache auth public keys / sessions ngắn hạn để chịu đựng restart service
  • Chuẩn hóa HTTP status codes (401 vs 403 vs 404 đúng RFC 9110)
  • Auth service cần dedicated synthetic monitoring & alerting riêng
3. GATEWAY & CLIENT RESILIENCE
  • Single Page Apps (SPA): Catch-all fallback route cần thông báo rõ ràng, tránh 404 mập mờ
  • Edge rules / CDN config changes bắt buộc phải đi qua quy trình CI/CD
  • Tách biệt health check endpoint của ingress routing và core backend
4. DEPENDENCY & FAILOVER MANAGEMENT
  • Bản đồ hóa phụ thuộc (Dependency Mapping) cả upstream API lẫn hạ tầng vật lý ngầm
  • Client-side retry logic bắt buộc có jitter + retry budget tránh cascading retry storm
  • Giám sát độ trễ và tỉ lệ lỗi phân theo từng vùng địa lý (per-region alerting)
