Giải Ảo: 1 Physical Core Có Bằng 1 vCPU?

⚙️ Hyper-Threading / SMT (Cơ chế phần cứng)
• 1 Physical Core = 2 Hardware Threads (Logical Cores).
• Bộ tính toán (ALU, L1/L2 Cache) chỉ có 1 bộ duy nhất, chỉ nhân bản thanh ghi trạng thái (Registers).
• 👉 Trên nhiều Cloud VM dùng SMT: 1 vCPU thường tương ứng 1 Hardware Thread.
💡 Thực Tế Hiệu Năng (Performance Trap)
• 2 vCPU không đồng nghĩa với 2 Physical Cores.
• SMT có thể tăng throughput tùy workload, nhưng không tương đương thêm một physical core.
• Tác vụ nặng (DB, HPC, Crypto): Thường tắt SMT để tránh tranh chấp nội tại Core.
1 Physical Core (1 Bộ Não) ──[SMT]──► 2 Hardware Threads (2 Cánh Tay) ──[Cloud]──► 2 vCPU

Cơ Chế Khóa: Period & Quota

CPU Period
Khung thời gian kiểm soát thực tế của CFS scheduler. Mặc định Linux cgroup là 100ms (100,000µs).
CPU Quota (Limit)
Tổng thời gian CPU (ms) tối đa được phép dùng trong 1 period. Cộng dồn từ tất cả các core chạy song song.
Công thức: quota (ms) = số vCPU × period × (limit % / 100)

Phân Chia Mềm: CPU Weight / CPU Shares

Hard Limit (CPU Quota)
• Giới hạn trần trên tuyệt đối (Upper Cap).
• Hết Quota là bị Throttle ngắt lập tức, bất kể Host đang rảnh 100% hay bận.
Soft Limit (CPU Weight / Shares)
• Cấp phát tỷ trọng tương đối khi Host bị tranh chấp (Full Load).
• `cpu.weight` (cgroup v2: 1-10000, default 100)
• `cpu.shares` (cgroup v1: default 1024)
# Ví dụ: Container A (Weight 100) vs Container B (Weight 300)
Tỷ lệ CPU phân chia khi Host bận: Container B nhận 75% CPU-time, Container A nhận 25% CPU-time

CPU Cache (L3/LLC) Contention

Cơ chế tranh chấp L3 Cache
Các CPU Cores trên cùng Socket chia sẻ chung bộ nhớ L3 (Last Level Cache). Hàng xóm chạy ứng dụng cache-heavy làm tăng áp lực lên shared L3, khiến cache lines của app bị evict thường xuyên hơn.
Hệ quả
Cache Miss tăng → phải truy cập cache thấp hơn hoặc DRAM → latency tăng, throughput giảm. CPU % vẫn bình thường nhưng tốc độ xử lý giảm.

Tranh Chấp Disk I/O & I/O Wait

cgroup I/O Limits
• io.max → Giới hạn trần IOPS / Bandwidth.
• io.weight → Phân bổ trọng số khi tranh chấp I/O.
• Tương tự CPU: max để giới hạn cứng, weight để phân bổ tương đối khi tranh chấp.
Chỉ số %wa (I/O Wait)
CPU idle trong khi hệ thống đang có I/O chưa hoàn tất.
%wa cao có thể là dấu hiệu I/O bottleneck, không đồng nghĩa CPU quá tải.

Tranh Chấp Memory Bandwidth

🧠 Bản chất: Băng Thông, Không Phải Dung Lượng
• Dung lượng RAM (Capacity) đã được Hypervisor cấp phát riêng cho từng VM.
• Nhưng Memory Controller & DRAM Bus là tài nguyên dùng chung (shared) giữa các socket/core.
• Hàng xóm chạy workload memory-intensive (quét bảng lớn, AI, in-memory cache) sẽ ngốn sạch băng thông bus.
⚠️ Dây Chuyền Tác Động (Chain Reaction)
VM A: Đọc/ghi RAM liên tục (Memory-heavy)
───────────────► A chiếm phần lớn Memory Bandwidth
───────────────► VM B truy cập RAM bị trễ (Wait cycles)
───────────────► Memory Latency ↑ / App Throughput ↓
👉 Lưu ý cốt lõi: Không phải "hàng xóm dùng nhiều RAM làm ta chậm", mà là "hàng xóm chiếm dụng hết băng thông Memory Controller".

3 Điều Quan Trọng Cần Nhớ

01. Throttling ≠ Steal
Quota Throttling là do app vượt limit. Noisy Neighbor (Steal time) là do Host bị quá tải thực sự.
02. Theo dõi %st
CPU Steal Time (%st) là metric đáng tin cậy nhất để chứng minh tranh chấp tài nguyên vật lý.
03. K8s Governance
Lên Kubernetes vẫn bị Noisy Neighbor ở tầng Pod nếu không thiết lập Resource Requests / Limits chuẩn.
